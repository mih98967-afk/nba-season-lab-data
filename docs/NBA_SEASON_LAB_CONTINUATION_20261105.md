## Что важно пользователю (сохранить)
1. Главный вопрос открытия сервиса: **«Нужно ли сегодня делать замены?»**; показывать KEEP/NOW/LATER на 7 и 21 день, умеренный риск, вывод + 2–3 причины.
2. Пять первичных разделов: Сегодня / Команда / Замены / Календарь / Игроки. Второстепенные страницы не удалять, а оставить в «Ещё».
3. Десктоп — приоритет. Состав из 10 игроков без скамейки, две карточки на позицию, современная визуальная баскетбольная площадка.
4. Пользователь начинающий в NBA, но сложные ограничения, модели, тесты и исследовательские инструменты внутри сохраняются.
5. Любой сценарий требует фактических Sports.ru цен, квоты, блокировки T−30, максимум двух игроков одного клуба, корректного счёта FP, клубной принадлежности и источников injuries; никакой автоматической передачи состава.

## Открытые задачи по порядку

### P0. Достоверность «делать ли замену сегодня»
- Проверить действительную страницу Hosting под реальным профилем владельца (не через публичную тестовую десятку): состав/касса/история/дедлайн и источники. Без чтения или экспорта личной Firebase-даты через публичный Git.
- Разобрать остаточное расхождение личных Sports.ru FP с модельной реконструкцией (ранее +5 FP для отдельных игр), сравнить бюджет и реальные остатки замен. Разница может быть в ET credit day, редакциях boxscore и подтверждении правила; не переписывать личные FP автоматически.
- В «Сегодня/Замены» выводить объяснимое решение KEEP/NOW/LATER с причинами и чёткими пометками: факт vs прогноз vs сценарий. Если цена/квота/свежесть/состав не подтверждены — совет условный, не «точная выгода».
- Проверить, что выбор краткого и длинного горизонта, multi-slot planner, корзина кандидатов и protected KEEP реально доступны и не перегружают интерфейс.

### P0. Непрерывность работы и релизы
- Исходники v6.19 — только кандидат `site/hosting_v619/`. Вливать после зелёных тестов; отдельно владелец публикует Existing Firebase Hosting. Не перезаписывать активную публикацию без QA на своём профиле.
- Не считать CI/browser tests на синтетическом roster подтверждением реальных Sports.ru операций.

### P1. Прогнозы как проверяемая модель
- Продолжить frozen genuinely prelock 2026/27 predictions и matched postgame outcomes. Запрещено post-hoc backdate; Git-as-of replay отделён от фактически выпущенных тогда прогнозов.
- Улучшать P(play), minutes-if-play и FP/min только при достаточно независимой оценке на новых датах; DNP/OUT/UNKNOWN различать, «не встретилось в boxscore» не равно DNP; полный P(play пока некалиброван.
- Раздельно анализировать MAE, калибровку, coverage и полезность реальных решений KEEP/NOW/LATER. Модель, улучшающая FP MAE на сыгравших, ещё не доказала, что улучшает замены.
- `research_only_not_deployed`, `adopt_on_site=false` для новых исследовательских моделей до отдельного решения.

### P1. Календарь и продукт
- Использовать дату NBA (ET) для тура, отображать время МСК, правильно трактовать ночные игры понедельника; фактический reset Sports.ru Пн 00:00 или 15:00 остаётся неподтверждённым — не выдавать две гипотезы за две квоты.
- Контекст отдыха/B2B считать только из валидного расписания, неизвестное обозначать «н/д». Не придумывать силу соперников: сначала независимая связь с будущими NBA fantasy FP на out-of-time holdout.
- Показать ясные 7/14/28-дневные окна, сумму матчей по своей десятке и отдельным игрокам, даты и бэк-ту-бэки. Затем оценить, действительно ли контекст отдыха меняет трансферное решение.

### P2. Качество данных и UX
- Freshness upstream ESPN/NBA/injury: один публичный writer, атомарные JSON, provenance и fail-closed; официальные injury отчёты выше Telegram.
- Проверка каждой страницы на десктопе и мобильном (отступы, читаемость, отсутствие лишнего текста), разделы «Ещё» и практический мини-гайд пользователя.

## Ограничения
Не создавать сайт, repo, Firebase-проект или новый Optimizer; не смешивать КХЛ/НХЛ. Без Lovable credits, платных API, Blaze и платных GitHub Actions. Не изменять приватный Firestore, реальные замены Sports.ru, состав, баланс, private backups, Hosting или модельные веса без отдельной проверки. Мерж PR и публикация Hosting — разные операции.

## Критерий «готово»
`source hash verification → relevant offline tests → PR CI PASS → merge → при необходимости public main sync SUCCESS → проверка production JSON → UI QA на настоящем профиле → отдельное подтверждение Hosting`. Для модельных изменений дополнительно нужен независимый prospective quality check.
