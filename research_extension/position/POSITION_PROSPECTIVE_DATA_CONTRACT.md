# Позиционная сложность: контракт следующей проверки

## Что разрешает уже сохранённый снимок

`results/FUTURE_POSITION_MAPPING.json` связывает 392 из 484 игроков публичного каталога с уникальным NBA person_id через точное нормализованное имя и уже существующий публичный мост catalog id → имя. Остальные 92 остаются UNKNOWN. Это позиции каталога сезона 2026/27 с явно сохранённым SHA, временем фактического наблюдения и источником. Они не объявлены независимо проверенным официальным Sports.ru справочником. Более ранняя дата, написанная внутри старого base.json, не заменяет доказательство времени наблюдения.

Позиционный прогноз может использовать запись только после `max(observed_at,effective_from)`, до `effective_until`, внутри указанного сезона. Конфликт двух действующих позиций закрывает вывод как UNKNOWN. Новый снимок не молча переписывает старый. Для корректировки записи нужен отдельный version с её собственным временем наблюдения. Эти записи не применяются к 1741 прогнозам от 16 ноября, выпущенным раньше нынешнего снимка.

## Формат будущей записи player×game

- Идентичность: NBA person_id, fantasy catalog_id, game_id, team, opponent, season.
- Время: issued_at, feature_cutoff, exact tipoff UTC/MSK, position_observed_at, position_effective_from/until.
- Источники: position_source_ref/SHA, schedule/model/source SHA, `mapping_status` и данные missingness.
- Прогнозы одновременно фиксируемых вариантов: исходный Ridge context; та же архитектура + общий opponent correction; та же архитектура + позиция; та же архитектура + position×opponent. Версии P(play) и интервалов одинаковы между сравниваемыми FP-вариантами.
- Выходы: E(FP|played), P(play), E(FP), условные и безусловные 50/80/95% интервалы при наличии собственной калибровки; отдельно unsupported, если диапазон ещё не валидирован.
- Статистика позиции×соперника: число игроков/матчей/дат, взвешенный объём, сила shrinkage, оценка относительно общей позиции по лиге, uncertainty. При отсутствии пригодной позиции residual можно учесть только в общей команде; нельзя условно назначать PG по G.

## Как определить именно позиционную добавку

В будущей исследовательской модели сначала строится ожидаемый результат игрока по его качеству, ожидаемым минутам, роли, отдыху и предматчевому темпу. Остаток после матча обновляет только последующие даты. Позиционная ячейка усаживается к общей поправке соперника, а общая поправка — к нулю. Базовые различия между PG и C нормируются отдельно: большой raw FP центрового не означает, что соперник легче для центровых. Полезность взаимодействия position×opponent измеряется поверх общего соперника и позиции в одной архитектуре и на одной когорте.

Количество известных позиций само по себе не даёт доказанной силы эффекта. Нужны заранее зафиксированные коэффициенты/семейство, walk-forward или future-frozen сравнение, MAE/RMSE/bias и калибровка по позициям; uncertainty с кластеризацией по матчам/датам и игрокам. Отсутствие официального credited Sports.ru FP не превращается в DNP/0. NBA replay, настоящие будущие outcomes и собственная fantasy-выгода показываются раздельно.

## Условие для интерфейса календаря

Пять позиций и 7/14/21/28 дней выводятся как количественная сложность только после подтверждённой добавочной прогнозной пользы. Пока статус — `position_effect_unvalidated`. Пользователю можно показывать число назначенных матчей, соперников и индивидуальный прогноз существующей модели с честной маркировкой; позиционные цвета или 1–5 баллов не выводятся.

При последующем допуске календарь хранит game-weighted среднюю сложность отдельно от числа игр, относительный matchup delta игрока и дату снимка; не складывает процентили. Интервалы суммы матчей требуют отдельной совместной калибровки. Данный контракт не создаёт scheduled workflow, не выпускает новых прогнозов и не меняет production.
